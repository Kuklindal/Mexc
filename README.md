# MEXC P2P: два участника, ручной и автоматический режимы

Один цикл: П1 продаёт USDT П2, затем П2 продаёт полученное количество USDT обратно П1.
По умолчанию действия подтверждаются в консоли; `--auto` выполняет заданное число циклов без ввода.
Один цикл — две сделки и пополнение объявления. Бесконечного повторения нет.
После завершения обратного ордера П1 добавляет полученное количество USDT в исходное объявление продажи.
Используйте для фактических сделок с реальными переводами и с учётом правил MEXC.

## Сценарий с подтверждениями

1. Оператор вводит сумму покупки П2 одной строкой, например `1000 RUB`, затем `advNo`
   **уже существующего объявления П1 о продаже USDT**. Число без валюты означает рубли.
2. После подтверждения объявления и способа оплаты программа от имени П2 открывает покупку на эту сумму.
3. Оператор сверяет ордер в обоих аккаунтах: участники, сумма, USDT, реквизиты.
4. П2 отправляет сообщение, П1 отвечает. Тексты вводятся в консоли.
5. П1 проверяет документы. В режиме `SELLER_CHECK_MODE=adspower` после подтверждения в консоли
   бот нажимает **«Проверка пройдена»** в открытом ордере профиля П1. В режиме `manual` кнопку нажимает оператор.
6. П2 фактически оплачивает сделку выбранным способом (наличные или перевод) и подтверждает оплату.
   Программа берёт ID реквизитов из `paymentInfo[].id` ордера и отмечает оплату.
7. П1 проверяет получение денег и подтверждает выпуск USDT.
8. Оператор подтверждает завершение первой сделки и получение USDT П2.
   **В Google Таблицу записываются количество USDT первой продажи, дата и время по Красноярску.**
9. П1 открывает своё объявление о **покупке** USDT, вводит его `advNo`.
10. П2 продаёт туда количество USDT из первой сделки. Сумма обратной сделки может отличаться.
11. После сверки ордера П2 пишет сообщение, П1 отвечает.
12. П1 оплачивает сделку и отмечает оплату. П2 проверяет получение денег и выпускает USDT.
13. Оператор подтверждает завершение обратной сделки.
14. Программа прибавляет полученные П1 USDT к исходному объявлению продажи после подтверждения оператора.
    После сверки пополнения цикл заканчивается.

`PAID` не доказывает поступление денег. Бот не подключён к банку и не делает банковские переводы.
В режиме с подтверждениями перед отметкой оплаты и выпуском нужно ввести отдельную фразу с номером ордера.
Пустой Enter не подтверждает действие. `STOP` или `Ctrl+C` останавливают сценарий.

## Подготовка на Windows

Из папки проекта в PowerShell (Python 3.11+, на этом компьютере есть 3.12):

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
if (!(Test-Path .env)) { Copy-Item .env.example .env }
notepad .env
```

Для API-режима заполните:

```dotenv
MEXC_P1_API_KEY=ключ_первого_аккаунта
MEXC_P1_SECRET_KEY=секрет_первого_аккаунта
MEXC_P2_API_KEY=ключ_второго_аккаунта
MEXC_P2_SECRET_KEY=секрет_второго_аккаунта
MEXC_P1_SELL_ADV_NO=номер_объявления_П1_о_продаже
MEXC_P1_BUY_ADV_NO=номер_объявления_П1_о_покупке
MEXC_P1_OVER_VERIFY='{"types":[1]}'
ENABLE_STATE_CHANGES=true

TELEGRAM_BOT_TOKEN=токен_бота
TELEGRAM_CHAT_ID=ID_чата

GOOGLE_SHEET_ID=ID_таблицы
GOOGLE_SHEET_TAB=Продажи
GOOGLE_SERVICE_ACCOUNT_FILE=credentials/google-service-account.json
```

Оба аккаунта должны иметь доступ к используемым P2P API. Ключи для спотовой торговли
не подтверждают такой доступ. Порядок подключения и документация — в
[MEXC Merchant Center](https://www.mexc.com/support/article/introduction-to-p2p-open-api-354433199621787648).
Если для ключа настроен список разрешённых IP, добавьте IP компьютера запуска.

Для каждой сделки понадобятся номера объявлений и ID способа оплаты/реквизитов из MEXC.
Номера объявлений можно один раз задать в `.env`: `MEXC_P1_SELL_ADV_NO` для первой продажи
и `MEXC_P1_BUY_ADV_NO` для обратной покупки П1. При заполненных настройках программа не спрашивает
номера, но показывает их перед подтверждением. Пустое значение сохраняет ручной ввод.
Новый цикл сохраняет эти номера в журнале; изменение `.env` не подменяет объявления уже начатого цикла.
Это внутренние ID биржи, **не номера банковских карт**. Программа запросит их перед операцией.
При отметке «Оплачено» ID реквизитов загружается из самого ордера. Если вариантов несколько,
выберите использованный вариант из списка. `payMethod` (например, 578) не заменяет `paymentInfo[].id`.
При обратной продаже нужен `id` активных реквизитов **П2** из его способов оплаты.
Код наличных `578` из объявления П1 для `userConfirmPaymentId` не подходит.
Ошибка `10013` означает, что MEXC не нашёл добавленные/активные реквизиты для запроса.
Чтобы не вводить ID П2 в каждом цикле, добавьте в `.env` строку `MEXC_P2_PAYMENT_ID=ваш_ID`.
Программа подставит его при обратной продаже и покажет перед подтверждением создания ордера.
При смене аккаунта П2 или удалении/пересоздании реквизитов обновите эту настройку.
[Официальная инструкция получения ID](https://www.mexc.com/api-docs/p2p/appendix/get-payment-user-id):
в аккаунте П2 откройте страницу способов оплаты, в F12 → Network найдите `/api/payment/user`;
нужен `data.id` записи с подходящим `data.payMethod`. Отдельного метода чтения списка
реквизитов по API-ключу эта инструкция не описывает.

## Запуск

**Один автоматический цикл:**

```powershell
.\.venv\Scripts\python.exe main.py cycle --auto --amount "9500 RUB" --count 1
```

**Серия из 10 циклов (20 сделок) со случайной суммой первой покупки от 9000 до 9500 RUB:**

```powershell
.\.venv\Scripts\python.exe main.py cycle --auto --min-amount 9000 --max-amount 9500 --count 10
```

Границы включены, шаг случайной суммы — 0,01. Оба порога должны укладываться в лимиты объявления.
Сумма выбирается заново на каждый цикл и сохраняется до открытия ордера.
Обратная сделка продаёт всё полученное количество USDT, её сумма в фиате зависит от цены объявления покупки.
Следующий цикл начинается только после завершения обеих сделок и пополнения объявления.
При ошибке или несовпадении участников внутри ордера самого цикла серия останавливается.
Другие ордера в тех же объявлениях игнорируются и не останавливают серию.
Случайные паузы, проверки участников и одна строка Google действуют на каждый цикл. Telegram автоматически сообщает только об ошибках.

Вместо параметров команды можно заполнить `.env`:

```dotenv
AUTO_MIN_AMOUNT=9000
AUTO_MAX_AMOUNT=9500
AUTO_FIAT=RUB
AUTO_CYCLE_COUNT=10
```

Тогда запуск: `.\.venv\Scripts\python.exe main.py cycle --auto`.
Параметры команды имеют приоритет; `--amount "9500 RUB"` отключает случайный выбор,
а `--count 1` явно ограничивает запуск одним циклом независимо от `.env`.
По умолчанию `AUTO_CYCLE_COUNT=1`, границы пустые.

После остановки используйте `cycle --resume ID_ЦИКЛА` без новых сумм и количества.
Программа продолжит сохранённый цикл и оставшуюся серию; уже выполненные циклы не повторяются,
выбранная сумма незавершённого цикла не меняется. Подходит ID любого цикла той же серии.
`--interactive` продолжит только выбранный цикл с подтверждениями; для продолжения оставшейся серии
после сверки снова запустите `cycle --resume ID_ЦИКЛА` без `--interactive`.

Сумма задаётся в фиате первой сделки. Оба объявления, реквизиты П2 и AdsPower должны быть настроены.
Дополнительные параметры `.env`:

```dotenv
ACTION_DELAY_MIN_SECONDS=20
ACTION_DELAY_MAX_SECONDS=30
MEXC_PAY_METHOD_ID=578
MEXC_P2_PAYMENT_ID=ID_реквизитов_П2
MEXC_P1_MEMBER_ID=memberId_П1
MEXC_P2_MEMBER_ID=memberId_П2
MEXC_P2_NICKNAME=Kuk_family818
# Необязательно: если пусто, П1 проверяется только по ID.
MEXC_P1_NICKNAME=
SELLER_CHECK_MODE=adspower
```

`578` — тип оплаты наличными. Для обратной продажи используется отдельный `MEXC_P2_PAYMENT_ID`.
Для нескольких аккаунтов П2 добавляйте отдельные блоки в `.env`. П1, его объявления и AdsPower остаются общими:

```dotenv
MEXC_P2_PROFILE=default
# Профиль default использует прежние MEXC_P2_API_KEY, SECRET_KEY, MEMBER_ID, NICKNAME, PAYMENT_ID.
MEXC_P2_2_API_KEY=ключ_второго_аккаунта
MEXC_P2_2_SECRET_KEY=секрет_второго_аккаунта
MEXC_P2_2_MEMBER_ID=memberId_второго_аккаунта
MEXC_P2_2_NICKNAME=точный_ник_второго_аккаунта
MEXC_P2_2_PAYMENT_ID=id_его_реквизитов
```

Выбор вручную при запуске (вся серия использует одного выбранного П2):

```powershell
.\.venv\Scripts\python.exe main.py cycle --p2-profile 2
.\.venv\Scripts\python.exe main.py cycle --auto --p2-profile 2 --min-amount 9000 --max-amount 9500 --count 10
```

Для третьего аккаунта добавьте `MEXC_P2_3_*` и используйте `--p2-profile 3`.
Допустимы и имена: `--p2-profile friend` соответствует `MEXC_P2_FRIEND_*`.
Без параметра используется `MEXC_P2_PROFILE` (по умолчанию `default`).
Для нового профиля задавайте его собственные ID, ник и реквизиты; `PAYMENT_ID` — не код способа оплаты `578`.
Отсутствующие поля не берутся из другого профиля. Проверки ID и ника разрешают только П2 выбранного цикла,
остальные настроенные аккаунты не становятся автоматически разрешёнными контрагентами этого цикла.
При `cycle --resume ID` профиль берётся из журнала независимо от текущего `MEXC_P2_PROFILE`.
Сменить профиль, API-ключ, закреплённый ID/ник или реквизиты начатого нового цикла нельзя.
Старые циклы без сохранённого имени профиля продолжаются через `default`.
Ключи в журнал не записываются; сохраняются имя профиля и отпечатки API-ключей.
Диагностика нужного П2: `python main.py detail НОМЕР_ОРДЕРА --account p2 --p2-profile 2`.

`memberId` берётся из сведений о контрагенте в проверенных ордерах обоих аккаунтов, это не никнейм.
В текущем `.env` участники уже привязаны по завершённым сделкам.
Сразу после создания каждого ордера, перед действиями и во время пауз бот читает
только сохранённые номера ордеров своего цикла. Из ответов обоих аккаунтов проверяются
ID П1 и П2, а для П2 дополнительно обязателен точный ник (регистр и символы должны совпадать).
Непосредственно перед выпуском USDT обе проверки выполняются повторно на свежих ответах API.
Отсутствующее поле или несовпадение в своём ордере блокирует действие с сообщением в Telegram.
Чужие ордера не выбираются по нику, их документы, оплата и средства не обрабатываются;
кнопка «Проверка не удалась» не нажимается. ID и ник работают совместно, одного совпадения недостаточно.
Для новых циклов разрешённые ID и ники сохраняются в журнале; подмена настроек при продолжении блокируется.
Проверка работает, пока запущен цикл; отдельного постоянного наблюдателя нет.

Автоматический режим использует тот же порядок операций и проверки статусов, что ручной.
По заданной настройке он сам подтверждает оплату, получение денег и проверку продавца
для разрешённой пары аккаунтов. Фактический перевод денег и содержимое документов программа не проверяет.
Если биржа требует дополнительный код или результат запроса неизвестен, цикл останавливается.
Автоматических повторов неизвестных операций нет.

Перед каждым изменяющим действием выбирается новая случайная пауза от `ACTION_DELAY_MIN_SECONDS`
до `ACTION_DELAY_MAX_SECONDS` (допускаются дробные секунды, границы от 0 до 3600).
Одинаковые границы задают постоянную паузу. Если обе границы отсутствуют, используется прежний
`ACTION_DELAY_SECONDS` или 20 секунд. Остановка — `Ctrl+C`.
После полного завершения цикла, включая пополнение, закрываются отдельные вкладки его ордеров
в подключённом профиле AdsPower П1. Совпадение проверяется по домену, пути и точному ID ордера.
Общая вкладка портала мерчанта, объявления и чужие ордера остаются открытыми.
У П2 профиль пока не подключён, поэтому его вкладки бот не закрывает.
Ошибка закрытия вкладок выводится в консоли и не приводит к повторению завершённых сделок.
Тексты четырёх сообщений редактируются в массивах `PHRASES` файла `phrases.py`;
для каждого шага случайно выбирается одна фраза. Прочтение чата с обеих сторон пока отключено:
`mark_chat_read` — заглушка, которая возвращает `False` и не отправляет запросов.

Продолжение сохраняет автоматический режим. Для сверки после неопределённого результата:

```powershell
.\.venv\Scripts\python.exe main.py cycle --resume ID_ЦИКЛА --interactive
```

Начатый ручной цикл нельзя переключить в автоматический; завершите его прежде, чем начать новый.

API-режим с ручным подтверждением каждой операции в консоли (`api` по умолчанию):

```powershell
.\.venv\Scripts\python.exe main.py cycle
```

Первые поля выглядят так (номер объявления ниже приведён только для примера):

```text
Сумма покупки П2 (например 1000 RUB; без валюты — RUB): 1000 RUB
П2 купит у П1 USDT на 1000 RUB.
Номер готового объявления П1 о продаже USDT (advNo): 123456789
```

Далее подтвердите готовое объявление, укажите ID способа оплаты и подтвердите создание сделки.
Программа использует существующее объявление и после обратной сделки пополняет его через API.
Для действий без ручного нажатия торговых кнопок включите `SELLER_CHECK_MODE=adspower` (настройка ниже).
Фактическая передача наличных/банковский перевод и проверка документов остаются за оператором;
отметка «Оплачено» через API сама деньги не переводит. Коды подтверждения MEXC вводятся в консоли.

Полностью ручной режим: операции выполняются на сайте MEXC, программа ведёт шаги и уведомления.
API-ключи и `ENABLE_STATE_CHANGES=true` для этого режима не нужны:

```powershell
.\.venv\Scripts\python.exe main.py cycle --mode manual
```

Просмотр прогресса и продолжение (ID программа показывает при запуске):

```powershell
.\.venv\Scripts\python.exe main.py cycle-status
.\.venv\Scripts\python.exe main.py cycle --resume ID_ЦИКЛА
```

Чтобы сбросить цикл и начать заново:

```powershell
.\.venv\Scripts\python.exe main.py cycle-reset ID_ЦИКЛА
```

Введите показанную фразу `СБРОСИТЬ ID_ЦИКЛА`, затем запустите `cycle`.
Сброс сохраняет историю, суммы продаж и очередь уведомлений. Ордеры на MEXC он **не отменяет**:
проверьте их на бирже перед новой сделкой. Сброшенный цикл продолжить нельзя.
Событие сброса сохранится в очереди и отправится при следующем цикле или `sync-journal`.

Режим и API-профили начатого цикла менять нельзя. Пока цикл не завершён или не сброшен, новый не запускается.
После сетевой ошибки результат операции может быть неизвестен. Создание ордера и сообщения
повторно автоматически не отправляются: требуется сверка с сайтом.
При продолжении создания выберите `СОЗДАН` и введите номер существующего ордера.
Если проверили историю обоих аккаунтов (включая закрытые ордера) и ордера попытки нет,
выберите `НЕ СОЗДАН`, подтвердите `ОРДЕР НЕ СОЗДАН ИМЯ_ШАГА`, исправьте реквизиты
и подтвердите новый запрос фразой `ПОВТОРИТЬ ИМЯ_ШАГА`. При сомнениях — `STOP`.
Для отметки оплаты и выпуска программа читает статус ордера в обоих аккаунтах.
Уже выполненная операция сверяется без повторной отправки. Если допустимый исходный статус
сохранился, повтор API-запроса требует отдельной фразы `ПОВТОРИТЬ ИМЯ_ШАГА` и подтверждения оплаты/получения денег.
Если результат нельзя подтвердить — `STOP`.
Не повторяйте банковский перевод только из-за ошибки API.

При явном отказе создания ордера `60085` (дневной торговый лимит) серия
приостанавливается, шаг сохраняется как `rejected`, а Telegram получает причину
и сведения о завершённой первой продаже. Повторный автоматический запуск не
отправляет заявку, не меняет П2 и не выполняет переводов или пополнения объявления.
После снятия ограничения на стороне MEXC используйте `cycle --resume ID --interactive`.
Программа отдельно запросит `ЛИМИТ ПРОВЕРЕН ИМЯ_ШАГА` перед подготовкой новой заявки.
Старый отказ `60085` на `reverse_create` распознаётся из ошибки последней попытки
в журнале; сетевой сбой или отказ до более поздней попытки таким подтверждением не считается.

При отказе пополнения `HTTP 400 / 700002` (неверная подпись), `60048` (лимит количества)
или `60064` (максимум сделки превышает стоимость объёма)
цикл сохраняет код отказа.
После исправления при `cycle --resume ID` повтор возможен только при неизменном остатке
и настройках объявления, с фразой `ПОВТОРИТЬ reverse_replenish`. Если целевой остаток уже
достигнут, программа только сверяет его. При таймауте без явного отказа эта возможность не применяется.

Для обратной продажи П2 отметку оплаты П1 можно отправить из `NOT_PAID` или `PROCESSING`
после подтверждения фактической оплаты оператором. `PROCESSING` сам по себе не подтверждает оплату:
если после запроса статус остался прежним, выпуск USDT блокируется.

В API-режиме выпуск возможен только при `PAID`, а завершение сделки и запись суммы — при `DONE`
(также принимается `COMPLETED`). Если при продолжении биржа уже возвращает `DONE`,
программа сверяет завершение без повторного выпуска и переходит к обратной продаже П2 в объявление П1 о покупке.
Статусы сверяются до и после финансовых запросов; неизвестный статус или расхождение аккаунтов останавливает сценарий.
Фраза `СВЕРЕНО` не заменяет проверку API. Если старый журнал ошибочно считает оплату выполненной,
а биржа возвращает `NOT_PAID`, при продолжении программа возвращается к шагу оплаты с новым подтверждением.

## Проверка документов через AdsPower

В `.env` можно настроить подключение к уже открытому SunBrowser профиля П1:

```dotenv
SELLER_CHECK_MODE=adspower
ADSPOWER_BASE_URL=http://127.0.0.1:53152
ADSPOWER_P1_PROFILE_ID=ID_профиля_П1
ADSPOWER_API_KEY=локальный_ключ_AdsPower
```

Оставьте AdsPower и профиль П1 открытыми, войдите в аккаунт П1 на MEXC.
На шаге проверки бот использует уже открытое окно нужного ордера либо открывает страницу
`/ru-RU/buy-crypto/order-processing?id=НОМЕР` в активной вкладке. Повторно такую вкладку не создаёт.
Если вкладка AdsPower не отвечает на чтение, бот переключается на неё и один раз повторяет чтение.
При таймауте самой команды нажатия повтор запрещён; цикл останавливается для сверки результата.
На шаге `forward_check` проверьте документы и введите `ДОКУМЕНТЫ ПРОВЕРЕНЫ НОМЕР_ОРДЕРА`, затем `ДА`.
Бот сверяет полный номер в окне ордера. На отдельной странице, где номер не показан текстом,
проверяет точный ID в адресе и заголовок состояния; другой видимый номер блокирует действие.
После подтверждений в консоли нажимает только кнопку «Проверка пройдена».
Успех подтверждается переходом этого же окна к «Ожидание оплаты» и серверным
`overVerifyState=1` из данных ордера в сессии П1. Статус `0` без признака требования проверки
считается неизвестным, а не ожиданием документов. Если сервер явно сообщает, что проверка не требуется,
бот пропускает кнопку и сохраняет отдельный результат `not_required`. Один заголовок не считается подтверждением:
отдельная страница иногда показывает ожидание оплаты, пока проверка ещё не пройдена.
В таком случае бот пытается открыть точный ордер через значок чата в «Мои ордера» портала мерчанта.
Если кнопка там недоступна, он останавливается. Перед отметкой оплаты серверная проверка повторяется.
При продолжении старого цикла ошибочная отметка проверки по одному заголовку перепроверяется.
Если появилось дополнительное подтверждение, изменился интерфейс или результат неясен,
цикл остановится: проверьте результат в браузере и завершите действие вручную перед продолжением.
Повторного автоматического нажатия после неизвестного результата нет.
Браузер после подключения остаётся открытым. Cookies, пароли и документы не выгружаются.
Прямая ссылка проверена на существующем отменённом ордере. Наличие кнопки и переход после
нажатия на отдельной странице ещё требуют проверки на активном ордере: если интерфейс отличается,
бот остановится. Полный цикл с настоящими средствами автоматически для тестирования не запускался.

Проверка подключения и кнопки **без нажатия**:

```powershell
.\.venv\Scripts\python.exe main.py adspower-check НОМЕР_ОРДЕРА
```

Для возврата к ручному нажатию установите `SELLER_CHECK_MODE=manual`.

## Telegram

Создайте бота через `@BotFather` → `/newbot`, сохраните токен в `.env`, отправьте своему боту `/start`.
Получите `message.chat.id` через `https://api.telegram.org/bot<ТОКЕН>/getUpdates` и впишите его в `.env`.
[Официальная инструкция Telegram](https://core.telegram.org/bots/tutorial).

Автоматически отправляются только ошибки и блокировки безопасности, включая проблемы записи Google.
Успешные циклы, обычная остановка оператором, сброс и промежуточные шаги не присылаются.
Старые сообщения об успехе из очереди тоже подавляются; полная история остаётся в журнале.
Ответы на кнопки и сообщение о запуске панели управления отправляются отдельно от уведомлений о сделках.

Запуск управления (AdsPower П1 должен оставаться открытым):

```powershell
.\.venv\Scripts\python.exe main.py telegram-control
# Или выбрать другого П2 для новых серий:
.\.venv\Scripts\python.exe main.py telegram-control --p2-profile 2
```

Перед запуском остановите прежний процесс `cycle`. Панель удерживает блокировку журнала:
второй процесс не сможет параллельно запускать сделки. Окно консоли панели должно оставаться открытым.
Запуск панели сам по себе не начинает и не возобновляет торговлю. Отправьте своему боту `/start` или `/menu`.

- **Продолжить** — продолжить незавершённый автоматический цикл и его оставшуюся серию с сохранённым П2.
- **Остановить** — прервать паузу сразу; отправленный запрос завершить и сохранить, следующий шаг не начинать.
  Открытые ордера MEXC не отменяются. Ошибка/неизвестный результат сохраняются по прежним правилам.
- **Новый цикл** — начать серию по `AUTO_MIN_AMOUNT`, `AUTO_MAX_AMOUNT`, `AUTO_FIAT`, `AUTO_CYCLE_COUNT` и выбранному П2.
  При незавершённом цикле новый запуск запрещён. Настройки `.env` загружаются при запуске панели; после правок перезапустите её.
- **Статус** — состояние работающей программы, текущий/последний цикл, П2, позиция в серии, последний шаг и номера ордеров.
  Это актуальное состояние локального журнала, а не отдельный запрос статуса оплаты в MEXC.
- **Сегодня** — статистика по Красноярску (UTC+7, с 00:00 до 24:00): завершённые полные циклы,
  первые продажи и обратные сделки, их объёмы USDT и суммы отдельно по каждой фиатной валюте.
  Учитывается время завершения каждого этапа, повторная сверка того же этапа не увеличивает статистику.

В личном чате команды разрешены только владельцу числового `TELEGRAM_CHAT_ID`.
Для группы задайте `TELEGRAM_CONTROL_USER_ID` — личный числовой Telegram ID оператора.
Одновременно проверяются чат и отправитель; остальные пользователи не могут запускать сделки или получать статистику.
Повторные Telegram updates и устаревшие кнопки не запускают операции повторно. После перезапуска используйте новое меню.
Начатые ручные циклы и неопределённые результаты операций по-прежнему требуют консольной сверки:
остановите панель и используйте `cycle --resume ID --interactive`; кнопка не обходит эту защиту.
Недоставленные ошибки сохраняются локально и повторно доставляются; при потере ответа Telegram возможно повторное уведомление.

## Google Таблица — USDT первой продажи и время

1. В Google Cloud включите **Google Sheets API**, создайте service account и скачайте его JSON-ключ.
2. Положите ключ в `credentials/google-service-account.json`.
3. Создайте Google Таблицу и отдельную пустую вкладку **Продажи**.
4. Откройте доступ к таблице для `client_email` из JSON с ролью **Редактор**.
5. В `GOOGLE_SHEET_ID` вставьте часть ссылки между `/d/` и `/edit`, в `GOOGLE_SHEET_TAB` — название вкладки.

Столбец A: «Сумма продажи (USDT)» — количество USDT первой завершённой продажи.
Столбец B: дата по Красноярску, столбец C: время (UTC+7). Одна строка на цикл.
Обратная продажа и подробные шаги в таблицу не записываются.
Сумма сохраняется сразу после подтверждения первой завершённой сделки, даже если обратная ещё не завершена.
Рубли не пересчитываются по курсу USD: записывается именно количество USDT.
Старая таблица с рублями переводится в этот формат по журналу только при совпадении прежних строк.

Вкладка выделена для программы: не сортируйте её и не вставляйте/удаляйте строки.
Повторная доставка записывает сумму в ту же ячейку, чтобы не создавать дубликаты.
[Метод записи Google Sheets](https://developers.google.com/workspace/sheets/api/guides/values).

Если Telegram/Google временно недоступны, сделки не повторяются, данные остаются в очереди.
После исправления подключения:

```powershell
.\.venv\Scripts\python.exe main.py sync-journal
```

## Ограничения и хранение

Для текущего API, который не возвращает `overVerify`, последний шаг `reverse_replenish`
использует отдельное действие сайта «Увеличить количество» через сессию П1 AdsPower:
`POST /api/platform/p2p/api/merchant/order/quantity`, только `id` и добавляемое `quantity`.
Полное пересохранение объявления `save_or_update` в этом случае не выполняется.
Цена, лимиты и требования к документам не передаются в запросе. Перед действием сверяются
остатки в API и браузере, а после — целевой остаток и фактический `overVerify`.
Дополнительная проверка должна быть включена и сохранена на сайте: значение из `.env`
не является доказательством того, что галочка включена. В авторежиме это проверяется до первой покупки.
При закрытом профиле П1, выключенной проверке, ошибке запроса или расхождении после пополнения
серия останавливается. Повторного увеличения количества после неизвестного результата нет.

Старый путь для ответов API с полным `overVerify` и ранее сохранённых планов использует
[`supplyQuantity`](https://www.mexc.com/api-docs/p2p/advertisement-management/save-or-update-ad).
Например: остаток 7,3051 USDT + возвращённые 101,6949 USDT = 109 USDT.
Количество берётся из завершённой обратной сделки; рублёвая сумма для пополнения не используется.
Обязательное поле `initQuantity` передаётся как целевой доступный остаток
(`availableQuantity + supplyQuantity`). Историческое поле `quantity` из списка объявлений
для него не используется: оно может превышать лимит количества объявления.
Перед запросом программа показывает `before_available` и `target_available`; без `--auto` ждёт `ДА`.
Цель: `target_available = availableQuantity + полученные USDT`; после запроса сверяется именно
доступный остаток `availableQuantity`. В API передаётся добавка через `supplyQuantity`.
Цена и минимальный лимит сохраняются. Если максимум сделки превышает стоимость целевого объёма,
программа покажет его снижение до этой стоимости (с округлением вниз до сотых).
Подтверждение пополнения в консоли также разрешает показанное изменение максимального лимита;
после запроса проверяются остаток и новый максимум. Если объём меньше минимального лимита,
запрос блокируется. Закрытое объявление автоматически не публикуется.
Нужны права ключа П1 `P2P Account Read` и `P2P Deal Ad`.

В старом пути полного обновления дополнительная проверка передаётся в `overVerify` как JSON-строка.
`MEXC_P1_OVER_VERIFY` из `.env` описывает желаемую настройку для прежних планов:
`{"types":[1]}` означает «Удостоверение личности».
Другие типы: 2 — паспорт, 3 — селфи, 4 — подтверждение адреса, 5 — выписка,
6 — другое (требуется `otherText`); максимум три типа. Если поле есть в ответе API,
его настройка сохраняется. Без известной корректной настройки пополнение блокируется.
Передача строки из `.env` сама по себе не гарантирует сохранение настройки сервером.
При неполном ответе API новый путь читает фактическую настройку через сессию браузера;
прежний полный запрос в этом случае не используется.

Если цикл завершён старой версией без этого шага, `cycle --resume ID` выполнит недостающее пополнение.
Если уже пополнили объявление вручную до запуска этого шага, не подтверждайте новое пополнение.
После неизвестного результата запроса автоматического повтора нет: сверяется сохранённый целевой доступный остаток.
При несовпадении проверьте пополнение на MEXC. Если запрос не сработал, добавьте сохранённое количество
вручную, затем продолжите цикл для сверки. Не прибавляйте эту сумму повторно при неясном результате.
Пополнение сохраняется в журнале; в Google Таблице остаются USDT и время первой продажи. Успешный цикл в Telegram не рассылается.

- Публикация объявлений выполняется на сайте. Проверка продавца — вручную либо через AdsPower;
  отдельного метода подтверждения проверки в изученной документации MEXC P2P API нет.
- REST/WebSocket-методы исходного проекта сохранены. Реальное подключение к MEXC нужно проверить на ваших аккаунтах.
  Без ключей тесты проверяют логику на имитации API, а не доступ к бирже.
- Программа сверяет номер, USDT, фиатную валюту, сумму и количество по обоим API-профилям.
  В режиме с подтверждениями оператор дополнительно сверяет перевод; в авторежиме такой проверки нет.
- Прогресс, события и очередь сумм: `data/cycles.sqlite3`. Сохраняйте папку `data` между запусками.
  Одновременный запуск двух процессов с одним журналом заблокирован.
- `.env`, `credentials/`, `data/` и `logs/` исключены из Git. Секреты и коды подтверждения в журнал цикла не записываются.
- Без Telegram/Google сценарий работает с локальным журналом; накопленные данные можно отправить после настройки.

Старые команды доступны; нужный аккаунт выбирается параметром `--account p1` или `--account p2`:

```powershell
.\.venv\Scripts\python.exe main.py detail НОМЕР_ОРДЕРА --account p1
.\.venv\Scripts\python.exe main.py monitor --account p2
```

Без `--account` используются прежние `MEXC_API_KEY` / `MEXC_SECRET_KEY`.
Проверки локальной логики: `.\.venv\Scripts\python.exe -X utf8 -m unittest discover -s tests -v`.
