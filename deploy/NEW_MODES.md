# Три режима Telegram

«Объём наличка»: один раз задайте `CASH_VOLUME_P1_PROFILE` и `CASH_VOLUME_P2_PROFILES` в `.env`. Нажатие кнопки в Telegram запускает серию с этими профилями без повторного выбора. В каждом новом цикле П2 покупает USDT через SELL-объявление П1 и продаёт их через BUY-объявление П1. Бот суммирует подтверждённые первые покупки этого П2 из журнала за скользящие 24 часа, включая предыдущие запуски и незавершённые обратные сделки. Цель — 69 000 USDT; если расчётный следующий ордер превысит 70 000 USDT, он не открывается. После завершения обратной сделки бот меняет П2 и ждёт, пока старые покупки выйдут из 24-часового окна. `CASH_VOLUME_FINAL_RETURN` не влияет на новые циклы; уже начатые циклы сохраняют свой старый маршрут и могут быть продолжены.

Оставляйте один работающий экземпляр с актуальным общим журналом: два независимых журнала не могут обеспечить общий 24-часовой счётчик. Если результат создания первого ордера в журнале остался неизвестным, П2 не получит новый ордер, пока эта попытка не выйдет из окна. Проверка перед отправкой использует текущую цену объявления и запас 0,5%; биржа может изменить цену после проверки, поэтому фактический объём сверяется после завершения первой сделки.

Сетевой и P2-maker маршруты остаются в коде для продолжения ранее сохранённых циклов; новые наличные циклы их не используют.

«Объём Eflp»: задайте `EFLP_VOLUME_P2_PROFILES` в `.env`, затем выберите П1 в Telegram. После выбора П1 серия запускается сразу, П2 идут в порядке из `.env`. Для каждого П2 отдельно бот выполняет обычные циклы через SELL и BUY П1 до 20 000 USDT подтверждённых первых покупок. Последний полный цикл может немного превысить порог. После выполнения плана по профилю бот сообщает его ник в Telegram.

«Уникальные Eflp»: задайте не менее 20 разных П2 в `EFLP_UNIQUE_P2_PROFILES`, затем выберите П1 в Telegram. Каждый П2 выполняет один полный цикл через SELL и BUY П1; первая покупка составляет случайные 50–100 USDT в пределах актуальных лимитов объявлений. Серия завершается после 20 успешно завершённых разных П2, даже если в списке больше 20 аккаунтов.

Во всех переменных выбора указывайте внутренние ключи аккаунтов из `ROLLOVER_PROFILES` (например, `default,2,3`), а не ники или `MEMBER_ID`. Для основного П1 используйте ключ `p1`. Один и тот же аккаунт нельзя выбрать одновременно П1 и П2. Изменения `.env` применятся после перезапуска Telegram-бота; уже сохранённая серия сохраняет свой список профилей.

В Eflp в каждом из двух ордеров после сообщений бот ждёт перед отметкой оплаты, затем снова ждёт перед подтверждением получения и выпуском USDT. По умолчанию каждая пауза случайна в пределах 75–105 секунд. Настройки: `EFLP_WAIT_MIN_SECONDS`, `EFLP_WAIT_MAX_SECONDS`. `CASH_REVERSE_WAIT_MIN_SECONDS` и `CASH_REVERSE_WAIT_MAX_SECONDS` относятся только к старым сохранённым наличным циклам с P2-maker возвратом. Сохранённое время окончания ожидания переживает перезапуск и не назначается повторно.

В Eflp нет шага «Проверка пройдена»: после сообщений и ожидания бот переходит к отметке оплаты. Для этих режимов не выполняется проверка кнопки через AdsPower перед оплатой. AdsPower П1 всё ещё нужен для работы с объявлениями.

В `.env` у выбранного П1 должны быть API-ключи, `MEMBER_ID`, `SELL_ADV_NO`, `BUY_ADV_NO` и профиль AdsPower. Для П1 из списка П2 используется префикс `MEXC_P2_<ключ>` (для `default` — `MEXC_P2`), для основного П1 — `MEXC_P1` и `ADSPOWER_P1_PROFILE_ID`. Для П2 в новых наличных и Eflp циклах достаточно API-ключей, `MEMBER_ID`, точного `NICKNAME` и `PAYMENT_ID`. Все выбранные аккаунты должны иметь разные `MEMBER_ID` и API-ключи.

В Google Таблице на том же листе появится таблица N:P: ник П1, объём подтверждённых первых продаж в режимах Eflp и количество разных П2 по `MEMBER_ID`. Формулы используют неделю, выбранную в G1 (четверг 18:50 МСК — следующий четверг 18:50 МСК). Служебные столбцы Q:S должны быть свободны. При каждом `sync-journal` данные и формулы обновляются. Существующее содержимое K:M не перезаписывается.

Старые сохранённые циклы и ончейн-возвраты остаются по прежнему маршруту. Не сбрасывайте цикл с незавершённым возвратом до сверки ордеров на MEXC. Бот не получает банковскую выписку и не может независимо удостоверить фактический фиатный перевод.

Для параллельной работы «Объём наличка» и Eflp на одном сервере запустите два процесса `telegram-control` из одного каталога с `MEXC_ENV_FILE=.env.cash` и `MEXC_ENV_FILE=.env.eflp`. В каждом файле задайте отдельный токен Telegram, `CYCLE_DB`, `LOG_DIR` и вкладку Google Таблицы (`GOOGLE_SHEET_TAB`). В этом варианте сводка Eflp N:P находится на отдельной вкладке Eflp того же Google-файла; оба процесса не должны синхронизировать одну вкладку из разных журналов. Аккаунты П1 и П2 между процессами не должны пересекаться: 24-часовой счётчик наличного режима видит только свой журнал. В обоих файлах установите `ADSPOWER_CLOSE_OTHER_PROFILES=false`, иначе экземпляры будут закрывать профили AdsPower друг друга. Одна служба AdsPower обслуживает оба процесса. Пример пользовательской службы: `deploy/mexc-parallel@.service.example`; для запуска после перезагрузки требуется `Linger=yes` или системная служба.

Для переноса кода на Linux остановите Telegram-серию, дождитесь конца текущего действия и сделайте резервную копию `data`. Не переносите поверх серверных `.env`, журнала и профиля AdsPower. Из каталога проекта Windows:

```powershell
tar -czf "$env:TEMP\mexc-code.tar.gz" --exclude=.venv --exclude=.git --exclude=.env '--exclude=.env.*' --exclude=data --exclude=logs --exclude=credentials .
scp "$env:TEMP\mexc-code.tar.gz" mexc@SERVER:~/mexc-code.tar.gz
```

На сервере:

```bash
cd ~/mexc_auto/rep
cp -a data "data.backup.$(date +%Y%m%d-%H%M%S)"
tar -xzf ~/mexc-code.tar.gz
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m unittest discover -s tests -p 'test_*.py' -q
systemctl --user restart mexc-telegram.service
```

Если бот запущен без пользовательской службы, вместо последней команды перезапустите ваш прежний процесс `telegram-control`. Только одна копия бота должна использовать токен и журнал. После запуска проверьте `/start`, выбранный режим и статус, прежде чем создавать ордера.
