# Режимы Telegram

«Объём наличка»: один раз задайте `CASH_VOLUME_P1_PROFILE` и `CASH_VOLUME_P2_PROFILES` в `.env`. Нажатие кнопки в Telegram запускает серию с этими профилями без повторного выбора. В каждом новом цикле П2 покупает USDT через SELL-объявление П1 и продаёт их через BUY-объявление П1. Бот суммирует подтверждённые первые покупки этого П2 из журнала за скользящие 24 часа, включая предыдущие запуски и незавершённые обратные сделки. Цель — 68 000 USDT; если расчётный следующий ордер превысит 70 000 USDT, он не открывается. После завершения обратной сделки бот меняет П2 и ждёт, пока старые покупки выйдут из 24-часового окна. `CASH_VOLUME_FINAL_RETURN` не влияет на новые циклы; уже начатые циклы сохраняют свой старый маршрут и могут быть продолжены.

Если AdsPower не ответил на `Runtime.evaluate` при пополнении объявления, серия ждёт 30 секунд и продолжает тот же цикл. Сначала сверяется доступный остаток объявления через MEXC и браузер; если пополнение уже прошло, второй запрос не отправляется. Пока AdsPower недоступен, серия остаётся в ожидании.

Оставляйте один работающий экземпляр с актуальным общим журналом: два независимых журнала не могут обеспечить общий 24-часовой счётчик. Если результат создания первого ордера в журнале остался неизвестным, П2 не получит новый ордер, пока эта попытка не выйдет из окна. Проверка перед отправкой использует текущую цену объявления и запас 0,5%; биржа может изменить цену после проверки, поэтому фактический объём сверяется после завершения первой сделки.

Сетевой и P2-maker маршруты остаются в коде для продолжения ранее сохранённых циклов; новые наличные циклы их не используют.

«Объём Eflp»: задайте упорядоченный `EFLP_P1_PROFILES` и `EFLP_VOLUME_P2_PROFILES` в `.env`. В Telegram достаточно нажать кнопку режима. Для каждого П1 бот выполняет циклы через SELL и BUY текущего П1, пока за текущую неделю не наберётся не менее 20 000 USDT первых покупок. Один П2 может выполнить несколько циклов; последний полный цикл может превысить 20 000 USDT. Число уникальных П2 не ограничивает этот режим.

После выполнения плана П1 бот делает отдельный финальный выкуп его SELL-объявления, оставляя 10–12 USDT. Если впереди есть следующий П1, тот же П2 продаёт выкупленное в BUY-объявление следующего П1; затем новый П1 пополняет своё SELL-объявление. Прежний браузер AdsPower закрывается после подтверждённого перехода. На последнем П1 USDT остаются у П2. Уведомление о завершении каждого П1 сохраняется в журнале и повторно доставляется при временной ошибке Telegram.

Для «Объём Eflp» программного минимума 200 USDT больше нет. Бот берёт верхний доступный лимит с учётом SELL и BUY объявлений П1 и выбирает сумму на 100–150 USDT ниже него. Если такой отступ не помещается между лимитами биржи, выбирается ближайшая допустимая сумма у верхней границы; минимум объявлений MEXC всё равно соблюдается.

«Уникальные Eflp»: задайте общий `UNIQUE_P2_PROFILES` (старое `EFLP_UNIQUE_P2_PROFILES` читается, если общий список пуст). Каждый П2 выполняет один полный цикл через SELL и BUY текущего П1; первая покупка составляет случайные 50–100 USDT в пределах лимитов объявлений. П2 засчитывается после завершения обоих ордеров. После 20 разных П2 происходит тот же переход к следующему П1. Для достижения цели нужно настроить не менее 20 подходящих П2 для каждого П1.

«Уникальные наличка»: в том же `.env`, с тем же журналом `CYCLE_DB` и вкладкой Google Таблицы, где настроен «Объём наличка», задайте один ключ П1 в `CASH_UNIQUE_P1_PROFILES` (например, `p1`) и `UNIQUE_P2_PROFILES`. В отдельном `.env.cash2` тоже можно указать `p1`, если этот бот использует отдельный журнал и в его файле настроены другие `MEXC_P1_*`. Достаточно одного подходящего П2 за запуск. После полного обратного ордера бот засчитывает П2 один раз за текущую расчётную неделю; полные циклы «Объём наличка» для того же П1 тоже входят в счётчик. Когда все П2 текущего списка отработали, серия заканчивается; добавьте других П2 и запустите режим снова. При 25 уникальных П2 серия одного П1 завершается после обычного возврата через его BUY-объявление, без дополнительного финального ордера. Если указаны несколько П1, сохраняется последовательный переход между ними.

Для Eflp задайте один `payMethod` на фиат, например `EFLP_PAY_METHOD_ID_KZT=...`: он выбирает тип оплаты первого ордера П2 в SELL-объявлении П1. Аналогично задаются `_GEL`, `_TJS`, `_KGS` и при необходимости `_RUB`. Для обратной продажи каждый П2 использует свой ID активных реквизитов `MEXC_P2_<профиль>_PAYMENT_ID_<FIAT>`. Бот сверяет общий метод с SELL-объявлением П1 и наличие числового ID П2 до запуска; окончательную пригодность реквизитов подтверждает MEXC при создании обратного ордера. Новые циклы Eflp не открывают AdsPower П2 для поиска ID. Для «Объём наличка» `MEXC_PAY_METHOD_ID` (обычно 578) задаёт тип оплаты первого ордера, а для обратного у каждого П2 нужен собственный `MEXC_P2_<профиль>_PAYMENT_ID`. Сохранённые циклы продолжаются со своими настройками.

Для просмотра `payMethod` без создания ордера запустите `MEXC_ENV_FILE=.env.eflp .venv/bin/python main.py ad-payments --p1-profile p1_3`. Команда читает SELL-объявление П1 через подписанный Merchant API и выводит только ID методов, не реквизиты карты. ID собственных реквизитов П2 из этого объявления получить нельзя; официальный способ MEXC — `/api/payment/user` в авторизованном браузере нужного П2.

Для подготовки `.env.eflp` на компьютере с AdsPower можно выполнить `python main.py payment-ids --mode eflp --fiat KZT --profiles 3,12`; команда выведет готовые строки `MEXC_P2_3_PAYMENT_ID_KZT=...` и `MEXC_P2_12_PAYMENT_ID_KZT=...`. Если профиль AdsPower П2 не указан в `.env`, передайте его ID как `--profiles 3=k1example,12=k1another`. После переноса этих ID на сервер AdsPower П2 для новых сделок Eflp не нужен. Для налички проверяйте положительный `MEXC_P2_<профиль>_PAYMENT_ID` в `.env`.

Для Eflp перечислите П1 отдельно: `EFLP_P1_PROFILES=p1,p1_2,p1_3`. Основной П1 использует `MEXC_P1_*` и `ADSPOWER_P1_PROFILE_ID`, дополнительные — `MEXC_P1_2_*`, `MEXC_P1_3_*`, включая свои API, MEMBER_ID, NICKNAME, SELL_ADV_NO, BUY_ADV_NO и ADSPOWER_PROFILE_ID. П2 указывайте в `ROLLOVER_PROFILES` и `EFLP_VOLUME_P2_PROFILES` либо `UNIQUE_P2_PROFILES` как `MEXC_P2_<ключ>_*`. Указывайте внутренние ключи, а не ники или `MEMBER_ID`. П2, совпадающий с текущим П1 по `MEMBER_ID` или API-ключу, пропускается. Для каждого будущего П1 до запуска должны быть настроены BUY и SELL объявления, AdsPower и реквизиты П2 для его фиата. Изменения `.env` применятся после перезапуска Telegram-бота.

В Eflp в каждом из двух ордеров после сообщений бот ждёт перед отметкой оплаты, затем снова ждёт перед подтверждением получения и выпуском USDT. По умолчанию каждая пауза случайна в пределах 75–105 секунд. Настройки: `EFLP_WAIT_MIN_SECONDS`, `EFLP_WAIT_MAX_SECONDS`. `CASH_REVERSE_WAIT_MIN_SECONDS` и `CASH_REVERSE_WAIT_MAX_SECONDS` относятся только к старым сохранённым наличным циклам с P2-maker возвратом. Сохранённое время окончания ожидания переживает перезапуск и не назначается повторно.

Для Eflp можно отдельно задать четыре списка фраз в `.env.eflp`: `EFLP_FORWARD_MESSAGE_PHRASES` (П2 в первом ордере), `EFLP_FORWARD_REPLY_PHRASES` (П1), `EFLP_REVERSE_MESSAGE_PHRASES` (П2 в обратном ордере), `EFLP_REVERSE_REPLY_PHRASES` (П1). Варианты в каждом значении разделяются `|`. Пустые поля используют нейтральные фразы Eflp из `phrases.py`, а не фразы налички. Выбранные списки сохраняются в новом цикле; при восстановлении его фразы не меняются после правки `.env`.

В Eflp нет шага «Проверка пройдена»: после сообщений и ожидания бот переходит к отметке оплаты. Для этих режимов не выполняется проверка кнопки через AdsPower перед оплатой. AdsPower П1 всё ещё нужен для работы с объявлениями.

В `.env` у каждого П1 должны быть API-ключи, `MEMBER_ID`, `SELL_ADV_NO`, `BUY_ADV_NO` и профиль AdsPower. Для Eflp задайте валюту каждого П1: например, `MEXC_P1_3_FIAT=GEL`, `MEXC_P1_4_FIAT=KZT`. SELL и BUY объявления одного П1 должны иметь эту валюту. Для каждого подходящего П2 Eflp укажите `MEXC_P2_<профиль>_PAYMENT_ID_<FIAT>` для валюты соответствующего П1; AdsPower П2 новому циклу не требуется. Для налички П2 нужен `PAYMENT_ID` без суффикса валюты. Уже начатый цикл использует сохранённый способ оплаты и прежний маршрут.

В Google Таблице строки продаж A:E содержат сумму USDT, дату, время, П2 и П1. Видимая недельная таблица Eflp находится рядом с продажами в F:I: П1, число уникальных П2 с полными циклами по `MEMBER_ID`, сумма первых продаж П1 в USDT и «Итого USDT»: 90 при не менее чем 20 уникальных П2 и сумме строго больше 20 000 USDT, иначе 0. На листе «Продажи» блок «Уникальные наличка» занимает V:W: П1 и число уникальных П2 с полными циклами. Неделя выбирается в G1 (четверг 18:50 МСК — следующий четверг 18:50 МСК); отображение пересчитывается при выборе другой недели, а торговый прогресс всегда использует текущую неделю. Служебные столбцы R:U должны быть свободны. Уже занятые V:W не перезаписываются.

Старые сохранённые циклы и ончейн-возвраты остаются по прежнему маршруту. Не сбрасывайте цикл с незавершённым возвратом до сверки ордеров на MEXC. Бот не получает банковскую выписку и не может независимо удостоверить фактический фиатный перевод.

Для параллельной работы «Объём наличка» и Eflp на одном сервере запустите два процесса `telegram-control` из одного каталога с `MEXC_ENV_FILE=.env.cash` и `MEXC_ENV_FILE=.env.eflp`. В каждом файле задайте отдельный токен Telegram, `CYCLE_DB`, `LOG_DIR` и вкладку Google Таблицы (`GOOGLE_SHEET_TAB`). В этом варианте видимая сводка Eflp F:I находится на отдельной вкладке Eflp того же Google-файла; оба процесса не должны синхронизировать одну вкладку из разных журналов. Аккаунты П1 и П2 между процессами не должны пересекаться: 24-часовой счётчик наличного режима видит только свой журнал. В обоих файлах установите `ADSPOWER_CLOSE_OTHER_PROFILES=false`, иначе экземпляры будут закрывать профили AdsPower друг друга. Одна служба AdsPower обслуживает оба процесса. Пример пользовательской службы: `deploy/mexc-parallel@.service.example`; для запуска после перезагрузки требуется `Linger=yes` или системная служба.

Для второго независимого бота «Объём наличка» создайте `.env.cash2` копированием `.env`. В нём задайте отдельные `TELEGRAM_BOT_TOKEN`, `CYCLE_DB=data/cash2.sqlite3`, `LOG_DIR=logs/cash2`, `GOOGLE_SHEET_TAB=Продажи2`, `CASH_VOLUME_P1_PROFILE`, `CASH_VOLUME_P2_PROFILES` и `ADSPOWER_CLOSE_OTHER_PROFILES=false`. П1 и П2 двух ботов должны быть разными: если они совпадут, независимые журналы не смогут гарантировать общий лимит. Не копируйте старую базу в `cash2.sqlite3` для нового набора аккаунтов. Для пользовательской службы на сервере:

```bash
cd ~/mexc_auto/rep
cp .env .env.cash2
nano .env.cash2
mkdir -p ~/.config/systemd/user
cp deploy/mexc-parallel@.service.example ~/.config/systemd/user/mexc-parallel@.service
systemctl --user daemon-reload
systemctl --user enable --now mexc-parallel@cash2.service
systemctl --user is-active mexc-parallel@cash2.service
journalctl --user -u mexc-parallel@cash2.service -n 30 --no-pager
```

Проверьте `loginctl show-user "$USER" -p Linger`: при `Linger=no` пользовательская служба не запускается после перезагрузки до входа пользователя. Для постоянного автозапуска администратор сервера должен включить linger или установить системную службу. Не запускайте вторую копию того же Telegram-бота вручную поверх службы.

Для ручного открытия или закрытия одного браузерного профиля по ID AdsPower используйте `MEXC_ENV_FILE=.env.eflp .venv/bin/python main.py browser-open k1fpushv` и `MEXC_ENV_FILE=.env.eflp .venv/bin/python main.py browser-close k1fpushv`. Для наличного режима замените файл настроек на `.env` или `.env.cash`. Эти команды не закрывают другие профили и не требуют загрузки страницы MEXC. Старый `adspower-open` по-прежнему открывает П1 из настроек и проверяет страницу MEXC.

Для переноса кода на Linux остановите Telegram-серию, дождитесь конца текущего действия и сделайте резервную копию `data`. Не переносите поверх серверных `.env`, журнала и профиля AdsPower. Из каталога проекта Windows:

```powershell
tar -czf "$env:TEMP\mexc-code.tar.gz" --exclude=.venv --exclude=.git --exclude=.env '--exclude=.env.*' --exclude=data --exclude=logs --exclude=credentials .
scp "$env:TEMP\mexc-code.tar.gz" mexc@SERVER:~/mexc-code.tar.gz
```

На сервере:

```bash
cd ~/mexc_auto/rep
cp -a data "data.backup.$(date +%Y%m%d-%H%M%S)"
tar -xzf ~/mexc-code.tar.gz
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m unittest discover -s tests -p 'test_*.py' -q
systemctl --user restart mexc-telegram.service
```

Если бот запущен без пользовательской службы, вместо последней команды перезапустите ваш прежний процесс `telegram-control`. Только одна копия бота должна использовать токен и журнал. После запуска проверьте `/start`, выбранный режим и статус, прежде чем создавать ордера.
